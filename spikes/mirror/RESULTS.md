Mirror mode `slow` (5 s before replying), five sequential GETs per case. `mirror arrival - send` is the mirror request's arrival timestamp minus the moment the client sent the request. `mirror finish - primary response` shows how long the mirror stream stayed open after the client already had the primary's answer. With the primary sleeping 200 ms the mirror copy arrives ~200 ms before the primary responds; with a zero-latency primary the two land on either side of each other, i.e. the copy is issued concurrently and is not ordered against the primary response.

## Envoy Gateway route.go v1.9.2 evidence

Fetched from `https://raw.githubusercontent.com/envoyproxy/gateway/v1.9.2/internal/xds/translator/route.go` (blob sha 857003f1f4f2a38eb39491b727169d195e74768a, 977 lines). `buildXdsRequestMirrorPolicies` is called for both `httpRoute.Mirrors` sites (route.go:79-93) and reads:

```go
func buildXdsRequestMirrorPolicies(mirrorPolicies []*ir.MirrorPolicy) []*routev3.RouteAction_RequestMirrorPolicy {
	var xdsMirrorPolicies []*routev3.RouteAction_RequestMirrorPolicy

	for _, policy := range mirrorPolicies {
		if mp := mirrorPercentByPolicy(policy); mp != nil && policy.Destination != nil {
			xdsMirrorPolicies = append(xdsMirrorPolicies, &routev3.RouteAction_RequestMirrorPolicy{
				Cluster:         policy.Destination.Name,
				RuntimeFraction: mp,
				// We don't need to append the shadow host suffix as the mirror policy already uses a different cluster which is enough to distinguish the mirrored traffic
				DisableShadowHostSuffixAppend: true,
			})
		}
	}

	return xdsMirrorPolicies
```

So an HTTPRoute `RequestMirror` filter becomes a route-level `request_mirror_policies` entry with `disable_shadow_host_suffix_append: true`, matching `envoy.yaml` here. Issue https://github.com/envoyproxy/gateway/issues/7227 ("Remove shadow host suffix from the mirrored requests") is the change that introduced it; the fix went in with the comment quoted above.


## Conclusions against the DESIGN.md assumptions

| DESIGN.md assumption | verdict | evidence |
|---|---|---|
| POST body is mirrored whole | PASS | 6b8aa1a72be15d3bd8e76e6427f6f1c99505826b05f55232ad9faa5e25dc998e (len 5149, truncated=False); f2db9523a90e3b33747211678d94a626892b1dfb99a5a3f64a6f042b16aafa43 (len 70000, truncated=False) |
| method, path and query are preserved | PASS | measurements 1 and 2: request targets identical at the mirror |
| Authorization and User-Agent survive mirroring | PASS | measurement 1: both headers byte-identical at the mirror |
| Host is preserved (no -shadow suffix) | PASS | measurement 3: with the gateway's flag the mirror sees 'yattee.janpuc.com', without it 'yattee.janpuc.com-shadow' |
| a slow, dead or erroring mirror does not delay or fail the client | PASS | measurement 4: p50 stays at the primary's own latency in all four modes |
| no delivery guarantee and no ordering against the primary | INFO | measurement 6: the mirror request is issued concurrently with the primary request, its arrival timestamp lands on either side of the primary response, and its 5 s reply is discarded long after the client was served; measurement 4 confirms the client never waits |

Reading of the numbers, per assumption:

1. **POST body replicated.** The mirror received a byte-identical body (same sha256, same length) for the 5 KB and 70 KB feeds, for 1 MiB x10, 2 MiB x5, 512 KiB x3 and 64 KiB x3 in measurement 5. There is no truncation or size cut-off between 64 KiB and 2 MiB.
2. **Path, query, method and headers preserved.** The mirror's request target, `Authorization` and `User-Agent` match what the client sent, character for character.
3. **Host preserved.** With `disable_shadow_host_suffix_append: true` the mirror sees `yattee.janpuc.com`; without it Envoy appends `-shadow`. Envoy Gateway v1.9.2 sets the flag, so serendip sees the original Host and must accept any Host anyway.
4. **The primary is unaffected.** Client latency tracks the primary's own latency with the mirror normal, slow (5 s), erroring and stopped; no request failed and no response body changed. Mirror delivery stops when the mirror is down, and nothing else notices.
5. **Best effort.** Mirrored copies are not ordered against the primary response and have no delivery guarantee: Envoy keeps the shadow stream open after the client already has its answer, and while the mirror cluster has no healthy host (for example right after the mirror restarts) it answers the shadow requests locally with 503 and the copy is simply lost, with no retry. The client sees none of it.


## Caveats: how this differs from the live gateway

- This is a hand-written static bootstrap, not the xDS output of Envoy Gateway. What it copies is the part that matters here: the route-level `request_mirror_policies` entry with `disable_shadow_host_suffix_append: true`, as read from `route.go` at tag v1.9.2. The real gateway adds its own HCM settings, timeouts, retries and TLS; none of those change how a mirror stream is created.
- The mirror's mode is switched through `out/mode.txt`, which `mirror.py` re-reads per request, and `stopped` means the container is not running. This is a harness device, not part of the design.
- Every request carries a unique `X-Spike-Tag` header and each mirror record is matched on it, so a record can never be attributed to the wrong request. The large-body measurement repeats each size because a single attempt is not evidence.
- After the mirror container is restarted, the harness waits until Envoy reports the mirror cluster healthy again. In that window Envoy has no healthy mirror host and answers shadow requests locally with 503 (`upstream_cx_none_healthy`), which is the `stopped` case of measurement 4 and a real property of mirroring, not a harness bug.
- Plain HTTP on one host (OrbStack, containers side by side): no TLS, no Cloudflare hop, no cross-node network. Latencies here are lower bounds; the ordering and non-blocking results do not depend on that.
- One client at a time, sequential requests, HTTP/1.1 with the app's headers. Envoy's behaviour under concurrency or a full mirror cluster was not measured.
- The 5 s slow mirror is far below the route `timeout: 30s`; a mirror that never responds was not tested, but a stopped mirror was (Envoy's connections to it fail or time out, and the client is unaffected either way).
- The live gateway was not touched; `disable_shadow_host_suffix_append: true` is taken from the source at tag v1.9.2, and the counter-check on port 10001 shows what the same route looks like without it.
